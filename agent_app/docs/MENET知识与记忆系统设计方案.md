# MENET 知识与记忆系统设计方案

日期：2026-10-12。状态：供后续实现与评审的设计稿，尚未接入运行系统。

2026-10-14 范围确认（修订）：知识检索、上下文记忆、历史实验查询与受控参数优化均属于必须建设的能力，可分阶段交付。知识用于指导建议，参数优化通过用户授权和预算内的真实实验验证建议；不自动改写 MENET 源码或网络结构。第 21 节描述知识层，第 22 节明确参数优化要求；前文完整经验进化、策略优化与复杂展示保留为研究参考。

## 1. 设计依据与边界

依据当前目录中的《MENET智能体研究进展总结》以及两篇用户提供的论文：

- Dynamic medical knowledge graph updating method based on LLM decision control：借鉴候选知识、受控更新动作、多源反馈与可追踪更新机制。
- MemEvolve: Meta-Evolution of Agent Memory Systems：借鉴 Encode、Store、Retrieve、Manage 四模块和根据任务反馈改进记忆策略的方法。

初稿未读取实际后端代码或数据库，因此以下表名、接口名和接入位置均为建议，不代表现有实现。2026-10-14 已结合当前服务器代码核对会话状态、历史记录与 LLM 接入方式，核查结论和当前范围见第 21 节。论文中的提示、示例和代码仅作为研究材料。

第一版目标：让 MENET 能引用专业依据、恢复项目上下文、利用经过验证的历史经验，并说明建议的来源和适用条件。记忆辅助规划与解释，工具层继续决定执行合法性。

## 2. 先定义智能体应记住什么

### 2.1 专业知识

回答“为什么这样分析”：MENET 原理、输入格式、软件参数、基因组预测验证策略、数据泄漏与跨环境泛化的限制。

每条知识关联原文位置、原文片段、来源版本、适用范围。论文中的实验结果标记为特定实验条件下的证据，不能直接转换为默认运行参数。

### 2.2 项目状态

回答“我们正在做什么”：用户、项目、数据集与版本、目标性状、环境、研究目标、用户明确选择的模型、计算预算、当前步骤。

以结构化状态维护。当前任务的用户明确指示覆盖历史默认值；指示范围结束后不自动永久改写个人偏好。对象被删除、归档或版本变化时重新核验。

### 2.3 实验经历

回答“具体发生过什么”：任务输入、配置、数据划分、随机种子、软件与设备信息、状态、指标、工具错误、输出位置。

任务表、模型表和结果文件是事实来源。记忆保存索引或摘要；展示当前模型状态和精确指标时重新读取业务记录。运行失败与失败原因已确认分别表示。

### 2.4 可复用经验

回答“下一次可以怎样做”：经过验证的排错步骤、检查顺序、流程模板、带条件的参数比较和耗时经验。

每条经验必须包含触发条件、采取操作、观测结果、证据引用、适用范围和失效条件。未验证的模型反思只能成为候选经验。

## 3. 推荐架构

在现有应用后端增加 KnowledgeMemoryService，供聊天规划、工具调用准备和结果解释调用。沿用 SQLite、任务与模型记录及结果文件，先增加全文检索，确有语义召回需求时增加可重建的向量索引。

数据流：

1. 用户请求进入：读取有效项目状态并识别任务阶段。
2. 执行前：查询真实数据与模型信息，检索适用知识和经验。
3. 规划：生成带来源的建议或执行计划。
4. 执行：现有工具层校验并执行。
5. 执行后：保存工具事件和输出；从事件提炼候选经验。
6. 管理：校验、去重、修订、标记过期，保存更新记录。

失败时可以回退到无经验检索的原有流程。专业解释缺少来源时明确证据不足。记忆服务错误不能把任务误标为计算失败。

## 4. 建议的数据结构

### 4.1 sources：来源

字段：source_id、source_type、title、locator、content_hash、version、published_at、ingested_at、access_scope。

来源类型包括论文、软件文档、工具输出、用户明确陈述。公开文献与私有实验采用不同访问范围。一个来源可以支持多条知识或经验。

### 4.2 memory_items：知识与经验条目

字段：item_id、kind、content、scope_json、conditions_json、verification_status、lifecycle_status、created_at、last_verified_at、supersedes_id、revision。

- kind：domain_knowledge、experiment_observation、procedure、user_preference。
- scope_json：用户、项目、物种、数据集版本、性状、环境、软件版本等适用范围；未知与通用显式区分。
- conditions_json：前置条件、动作、结果和失效条件。
- verification_status：unverified、source_checked、tool_verified、replicated、reviewed。不同状态表示证据类型，不构成统一的置信度排名。
- lifecycle_status：candidate、active、disputed、superseded、archived、rejected。

单次任务观察可以在范围内成为 active；跨数据集通用建议需要另外验证。主张文本与不可变原始证据分开保存。

### 4.3 memory_evidence：证据关联

字段：evidence_id、item_id、source_id、source_locator、excerpt_or_reference、relation、task_id、artifact_hash。

relation 表示支持、反驳或限定条件。同一任务的多个摘要不能当成多次独立验证。保存页码、章节或结果文件字段等位置，确保可以回到原始证据。

### 4.4 project_state：项目状态

字段：project_id、user_id、dataset_id、dataset_version、trait、environment_scope、model_id、objective、stage、constraints_json、updated_at、revision。

数据集更换后清除或重新验证依赖旧数据集的模型和步骤状态。显式记录用户已确定的选择，恢复会话时显示必要的上下文摘要。

### 4.5 task_events：任务事件

字段：event_id、task_id、event_type、tool_name、input_reference、output_reference、observed_status、error_code、timestamp、idempotency_key。

按事件收集可观察的输入、动作和结果；无需保存模型隐藏推理。事件索引与原始输出关联，避免复制大型基因型文件。

### 4.6 memory_changes：更新审计

字段：change_id、item_id、action、before_revision、after_revision、reason、evidence_ids、actor_type、policy_version、timestamp、idempotency_key。

状态变化、证据关联和审计写入使用数据库事务。同一完成事件重复投递不会重复生成经验。修订保留旧版本；回滚不删除原始任务证据。

### 4.7 retrieval_events：检索记录

字段：request_id、task_id、stage、policy_version、candidate_ids、selected_ids、exclusion_reasons、context_size、latency、subsequent_outcome_reference。

用于诊断没有召回、召回不适用、上下文过长和经验未被使用的问题。被检索或使用不等于经验正确；使用频次与证据质量分开维护。

以上字段需要与真实后端的主键、权限、迁移方案对齐后实施。

## 5. 记忆读写接口

建议内部接口：

- retrieve_context(request)：按身份、项目、对象版本、任务阶段和查询返回条目、来源及适用条件。
- record_task_event(event)：从工具层记录观测事实，支持幂等写入。
- propose_memory(task_id)：生成候选经验及关联证据，不直接激活。
- validate_candidate(item_id)：检查来源存在、字段匹配、适用范围、重复与冲突。
- apply_memory_action(item_id, action, reason, evidence_ids)：按策略执行新增、修订、降权或拒绝并审计。
- update_project_state(patch, expected_revision)：对用户明确选择及工具事实更新状态，检测并发冲突。

服务返回结构化数据；聊天层负责解释。对外 MCP 首期优先提供受权限约束的读取工具，记忆写入经内部任务事件和校验路径完成。

## 6. 检索策略：先确定能不能用，再比较相关性

先做权限过滤，再判断条目类型、生命周期、对象版本及适用条件；随后采用精确匹配、全文检索与语义检索召回，最后根据来源、任务阶段和上下文预算选择内容。

专业知识允许使用明确标注为通用的条目；模型兼容性和实验经验必须核验必要条件。未知条件不能自动视为满足。项目经验与跨项目通用经验分开检索。

| 阶段 | 优先检索 | 必须实时核验 |
|---|---|---|
| 数据检查 | 格式要求、缺失值与样本匹配经验 | 当前文件与质量报告 |
| 分析设计 | 研究目标、划分策略、泄漏风险知识 | 当前样本、环境与分组信息 |
| 模型选择 | 用户选择、模型来源、可比较实验记录 | 模型状态、数据与预处理兼容性 |
| 训练 | 配置经验、耗时基准、已验证报错处理 | 参数合法性和设备状态 |
| 新样本预测 | 位点对齐流程、相关错误经验 | 位点集合、顺序、编码和预处理 |
| 结果解释 | 指标定义、研究背景、同协议基线 | 实际指标、划分与输出文件 |

模型比较只在性状、数据版本、评估目标、划分协议和指标定义可比时进行。选择与调参采用验证集或交叉验证；最终测试集用于独立评估，避免反复依据测试分数选择模型。

返回内容保留来源和条件，避免压缩为无条件建议。第一版通过固定上下文预算限制召回内容；具体条数由评测选择。

## 7. 受控更新策略

候选生成与激活分开。规则先检查引用完整性、对象存在性、指标一致性、兼容性和范围；大模型辅助识别文本重复、条件差异和潜在冲突，不能绕过规则。

- Add：创建有证据的条目，保留范围与验证状态。
- Revise：新增修订版本并关联旧版本；不同条件下的结论分别保留。
- Decay：降低当前检索优先级或标记不再适用；历史观察和审计记录保持完整。
- Reject：拒绝激活并记录理由，可保留候选供检查。

此外设置 disputed 状态：证据相互冲突或条件不足时待核验，不能把所有不确定内容都永久拒绝。

错误动作、超时或证据缺失时保持现有有效状态。候选文本包含操作指令时作为文档内容处理，不改变系统权限或工具规则。

时效性按内容类别管理：软件操作随版本重新验证；设备耗时随设备与规模变化更新；基础方法按新证据修订；历史实验按原始版本保留。不要套用统一时间衰减常数。

## 8. 一个完整案例：预测文件位点顺序不一致

1. 用户要求使用已选模型预测新样本。
2. 恢复项目状态，读取模型真实状态与预处理要求。
3. 工具检查发现集合一致、顺序不一致；返回明确诊断。
4. 检索相关的已验证经验，生成对齐建议。
5. 位点标识唯一且编码兼容等前置条件满足后，通过现有工具在派生文件中执行对齐。
6. 重新检查并执行预测，保存派生文件来源、配置、模型和结果。
7. 候选经验关联检查与修复事件；核验后成为限定范围的操作经验。

用户只上传了新文件但未要求预测时，经验不能触发额外预测。位点缺失或等位基因方向不明确时，对齐经验不能替代缺失处理或编码判断。

## 9. 现有模块的接入位置

- 聊天入口：构造检索请求，读取项目状态，显示引用与适用范围。
- 数据集解析和检查：记录数据版本、质量诊断和工具事件。
- 任务创建：保存研究目标、数据划分和完整配置快照。
- 任务完成或失败回调：幂等记录事件，异步生成候选经验；失败根因未经验证时保留为假设。
- 模型查询与预测前检查：读真实业务记录，调用相关经验检索。
- 结果解释：读真实输出，再检索方法知识和可比较经历。
- 管理界面：查看来源、状态、条件和修订记录，支持纠正与归档。

任务取消、超时和重试分别记录，不能都总结为算法失败。新增后台提炼工作有独立状态与预算，不阻塞已完成结果的返回。

## 10. 第一版交付顺序

### 阶段 A：来源与项目状态

实现文档导入、段落与页码定位、关键词检索、结构化项目状态、权限过滤。优先导入 MENET 官方方法与软件说明、现有操作文档和验证方法资料。

两篇参考论文用于系统设计；不要误当作 MENET 预测方法本身的领域证据。

### 阶段 B：任务经验

实现事件采集、候选提炼、证据核验和按阶段检索。优先覆盖数据格式、样本匹配、SNP 兼容性、模型选择和明确的工具错误。

### 阶段 C：维护与离线策略比较

实现版本修订、争议状态、归档、幂等更新和检索诊断。离线比较摘要粒度、关键词与向量召回、排序和上下文预算，通过评测后发布新策略。

暂不自动改写生产代码，不根据重复查看最终测试结果优化参数，不自动激活生成的可执行技能。

## 11. 评测与验收

建议先构建约 40 个有明确答案的业务场景，覆盖会话恢复、知识问答、模型选择、报错处理和结果解释。此规模用于开发回归检查，不足以证明科研效果或泛化提升。

比较四个版本：当前系统；增加专业知识检索；增加项目状态与任务经验；增加受控更新。固定模型服务、工具、数据和计算预算，保存每次运行的记忆快照与策略版本。

建立经验积累集、策略开发集和独立留出评测集；按项目或数据集分隔近重复场景。在线积累评测采用时间顺序，仅允许读取当前任务之前已产生的经验。

验收重点：

- 用户和项目隔离：预设越权场景无私有记忆泄漏。
- 对象恢复：旧模型归档、数据版本变化和用户改选后不沿用无效状态。
- 事实准确：模型 ID、任务状态和指标与实时业务记录一致。
- 来源可核验：激活条目可定位原文或工具输出，引用确实支持相应主张。
- 经验有条件：单次结果不升级为通用规律，相反结论按条件分别保留。
- 规则有效：语义相似但事实相反的内容不通过硬校验。
- 更新可恢复：重复事件不重复写入，修订可追溯，服务失败不破坏已有有效记录。
- 分析可靠：不利用最终测试集反复选择模型，不把成功运行等同于科学有效。

报告任务正确率、模型选择正确率、重复错误率、引用支持率、恢复准确率、检索延迟与调用成本。任务执行成功和科学建议正确分别计分。必要时重复运行，报告样本数量与波动。

## 12. 后续研究方向

可以研究“面向多环境基因组预测的证据约束任务记忆”：将物种、环境、数据版本和预处理一致性作为适用边界，结合失败经验与可验证工具反馈提升分析流程可靠性。

仅组合两篇论文的模块不足以构成新颖性。需要验证相对于普通文档检索、固定经验检索和规则系统的额外收益，并通过取消范围过滤、取消证据核验、取消任务阶段检索等消融解释收益来源。

记忆系统主要改善研究流程、建议和解释；它是否进一步改善预测指标，需要同数据、同预算、独立评估的额外实验，不能从聊天任务成功率推导。

## 13. 存储方案的具体选择

### 13.1 第一版采用 SQLite、文件存储和 FTS5

沿用现有业务数据库，在迁移核对后新增记忆相关表，使任务事件、证据关联和记忆状态尽可能在同一事务中提交。文件系统保存原始文档与结果，数据库保存身份、位置、版本和内容哈希。不要重复存储模型或大型基因型文件。

部署时检查 SQLite 的 FTS5 可用性，启用外键，使用短事务和有界写入重试。若应用部署在网络文件系统或多台服务器上，应重新评估数据库部署方式。多人并发写入和服务扩展成为实际瓶颈时，可以先迁移到 PostgreSQL；是否需要图数据库由关系查询需求单独决定。

FTS5 的默认分词不等于中文词语分词。导入和查询时采用同一版本的中文分词处理，将检索字段与原文分别保存；保留 MENET、SNP、R²、基因和参数标识的原始形式与规范化别名。通过中文问答及中英文混合查询验证召回率。短查询和编号优先精确匹配。

### 13.2 文档片段与知识条目分开

新增 source_chunks：chunk_id、source_id、source_version、page_start、page_end、section、raw_text、search_text、content_hash、parser_version。

文档片段是可定位的原材料，知识条目是经过解释和校验的主张。不能将“文档已导入”视为“所有主张已验证”。一条知识可以关联多个片段；一段原文也可能同时提供结论和限制条件。表格、图注和关键公式保留位置与解析状态，无法可靠提取时不自动生成确定性结论。

原始来源版本不可覆盖。更换文档时建立新版本，重新检查依赖条目；仅更新检索索引不改变条目的证据状态。

### 13.3 关系存储

第一版用关系表表达来源、依赖、修订与适用关系，不要求图数据库。

建议 resource_registry 保存受管理对象的 resource_id、resource_type、原业务对象 ID 与版本；memory_relations 保存 relation_id、subject_resource_id、predicate、object_resource_id、evidence_id、lifecycle_status。端点引用注册对象，避免无法校验的任意字符串关联。

关系类型采用有限集合，例如 derived_from、supports、contradicts、supersedes、applies_to、depends_on。数据集与模型的既有业务关系仍以原业务表为准；只在需要统一依赖查询时建立可校验的映射，避免产生两套互相冲突的事实。

实例：经验 E derived_from 任务 T；知识 K2 supersedes K1；经验 E applies_to 软件版本 V。查询某任务的经验或某条知识的证据，用普通关联查询即可。依赖传播可以先采用有深度与数量限制的递归查询。

只有在实际出现大量多跳关系查询、复杂路径解释和依赖遍历性能瓶颈时，再比较图数据库。届时迁移关系表示，保留现有对象身份、来源和版本。

### 13.4 向量检索作为可选增量

先用真实查询评测精确匹配与全文检索；如果同义表达、长问题和跨语言检索出现明显遗漏，再增加向量召回。

小规模候选集可先采用本地向量文件或适配的本地索引，按条目 ID 返回结果。实现选择需依据后端运行环境和检索基准，当前不指定未验证依赖。

向量索引记录 embedding_model、model_version、dimension、normalization、chunk_hash 和 index_version。修改片段或更换嵌入模型后重新构建；新索引完整后原子切换。不混用不同向量空间。索引中的删除或过期记录在返回前再次用数据库过滤。

查询必须先确定允许访问的范围；采用范围分区或支持预过滤的检索方式，不能先跨用户召回再将私有内容送给模型。数据库是条目状态与权限的事实来源，索引可重建。

## 14. 将知识更新组织为可验证的进化过程

### 14.1 三种版本分别记录

- knowledge_revision：知识与经验的内容、证据、适用范围和状态版本。
- memory_policy_version：提炼模板、检索规则、排序与维护策略版本。
- model_version：MENET 预测模型与模型服务的版本，二者分别记录。

知识更新不等于模型参数更新；换模型服务也不等于知识进化。分开记录才能定位行为变化来自何处。

### 14.2 日常内循环：更新知识与经验

触发事件包括文档新版本、任务完成、任务失败、用户纠正、软件升级和数据集版本变化。

流程为事件落库、候选提炼、证据检查、条件匹配、冲突分析、更新决策、事务写入、检索索引刷新。索引刷新可异步执行；查询时按数据库中的有效版本校验。

规则可以直接激活与工具输出一致且范围清晰的实验观察。模糊的根因推断、跨数据集推荐和影响多个流程的专业结论保留为候选或争议条目，补充证据后再处理。用户纠正优先记录为来源和待核验修改；用户对自己的目标或偏好的明确陈述可以直接更新相应项目状态。

记忆越多不是目标。候选的数量、使用次数、用户点赞和大模型自评不作为正确性的单独依据。重复来源合并，独立重复实验保留；相反结论先检查研究条件是否不同。

### 14.3 离线外循环：优化记忆策略

第一版采用人工可审查的策略配置：允许比较片段长度、经验字段、检索阶段、召回数量、全文与向量融合方式和上下文预算。保持工具校验、权限边界和原始证据不可被策略优化修改。

每轮先从检索事件诊断具体问题，再提出少量策略候选；用固定的经验快照和策略开发场景比较，以减少知识内容变化造成的混淆。需要评估在线积累能力时，另外按相同任务顺序从相同初始记忆运行各候选。

策略开发集可反复使用，但独立留出集不参与反复调参。记录每轮预算、候选数和选择过程；发布候选在留出场景上评估，持续迭代时补充新的留出任务，避免对评测集间接过拟合。

### 14.4 何时认为变好了

发布门槛分为必须满足的行为约束与可比较的效果指标。

必须满足：权限隔离、实际对象核验、来源定位、条件过滤、幂等更新与回滚场景全部通过预设回归检查。通过有限检查不意味着绝对无错误，但失败候选不能发布。

效果比较：在相同任务与预算下，任务正确率、模型选择正确率、重复错误率和引用支持率是否改善；同时报告响应延迟、模型调用成本和知识维护成本。优先采用配对比较并报告波动，样本不足时将改进标记为初步观察。

若正确率无改善但成本明显降低且关键场景不退化，也可以是有效的策略优化。若指标互有升降，根据提前确定的研究目标选择，不用一个任意加权分数掩盖关键错误。

### 14.5 发布与回退

发布记录包含策略版本、知识快照标识、评测场景版本、模型与工具版本、结果和选择理由。先用影子检索观察候选返回内容，不改变实际任务决策；确认后再启用。

知识内容回退与策略回退独立处理。策略问题回到上一策略版本；条目错误撤销其激活状态并追踪受影响的建议。实际已执行的实验与生成结果不能因记忆回退而被抹除。

## 15. 第一版可见行为示例

用户说“继续上次的预测”：系统恢复项目中的数据与模型选择，检查版本和状态；上下文存在多个合理任务时澄清目标。

用户说“为什么这次不能用那个模型”：系统读取实际检查结果，指出不兼容条件，关联软件说明与同条件下已验证的处理经验。

用户问“这组参数是不是更好”：系统区分单次观察、可比较重复实验和跨条件结论；依据验证协议说明证据强度，缺少比较证据时明确未知。

管理员问“这一版记忆系统有什么改善”：展示同任务配对评测中的错误变化、成本与延迟，给出知识更新与策略变化的版本记录。

最小成功标准是智能体能够明确说明：记住了什么、依据是什么、何时适用、何时失效，以及这项改变是否在独立场景中改善了行为。

## 16. 知识展示与更新可见性

知识系统不能只提供一个“已更新”提示。用户需要同时看到当前内容、证据状态、适用范围和变化原因，才能判断它是否影响自己的研究。展示层只读取已提交的条目版本和审计记录；候选经验不会在未核验时伪装成正式知识。

### 16.1 知识列表

新增“知识与记忆”页面，默认展示当前项目相关且处于 active、disputed 或 candidate 状态的条目，并支持按项目、物种、数据集版本、性状、阶段、类别、状态和变化类型筛选。

每行至少显示：标题或主张摘要、条目类型、适用范围摘要、证据状态、生命周期状态、变化类型、最近更新时间和来源数量。

变化类型和证据状态分开显示：

| 维度 | 标签 |
|---|---|
| 变化类型 | 新增、修订、降权、被替代、恢复 |
| 证据状态 | 待核验、来源已核验、工具已验证、多次实验支持、有争议 |
| 生命周期 | 候选、有效、争议、已替代、已归档、已拒绝 |

“刚更新”不等于“更可靠”，“旧”也不等于“失效”。颜色只作辅助，标签文字必须始终可见；颜色不能作为唯一状态信息。列表应显示一个小型“适用条件”摘要，防止用户把有条件的单次观察误读为普遍规律。

### 16.2 知识详情与版本对比

点击条目打开详情页，包含当前主张、适用条件、失效条件、证据来源、关联任务和当前版本。版本历史按时间倒序展示，支持选择任意两个版本进行差异对比。

每次变化显示：变化前内容、变化后内容、变化类型、触发事件、更新理由、证据关联、执行者类型、策略版本和时间。对于降权或被替代条目，显示当前仍可检索的范围，以及指向新条目的替代关系。

示例：

> 原内容：模型 M 可用于数据集 A 的新样本预测。  
> 更新后：模型 M 适用于数据集 A v2；预测前还需通过位点与编码兼容性检查。  
> 更新原因：补充模型预处理信息，并由兼容性检查任务验证。  
> 影响：后续预测流程增加版本、位点和编码核验。

原始文档片段、工具输出和任务结果使用可定位引用；无法定位的摘要显示为未核验，不提供“已由系统证明”的措辞。

### 16.3 更新动态

增加“更新动态”视图，按时间显示与当前项目相关的内容变化，支持按变化类型和状态过滤。默认突出可能影响当前工作的更新：模型适用范围变化、数据版本关系变化、操作经验通过工具验证、证据冲突和条目被替代。

动态记录使用条目版本和 change_id 去重。纯索引重建、重复导入和后台维护操作放入详细审计记录，不与知识内容变化混在同一条动态中。

推荐动态文案：

- “模型 M 的适用范围已修订，可能影响当前预测任务。”
- “SNP 对齐经验已通过工具验证，现可用于相同条件的预测前检查。”
- “两条参数建议证据冲突，已标记为有争议，暂不作为默认建议。”
- “新产生 1 条候选经验，尚未通过验证。”

动态页面需要显示变化前后版本，点击后进入详情；不要只显示“知识库已更新”。

### 16.4 聊天中的依据与记忆

在使用知识或经验的回答下方显示可展开的“依据与记忆”区域，包括使用条目数量、来源类型、条目状态和最近是否修订。每条引用可以跳转到知识详情或原文定位。

示例：

> 本次使用了 1 条软件说明和 2 条项目经验，其中 1 条经验最近已修订。查看依据与变化。

如果任务结束后只生成了候选经验，应显示：

> 已记录本次预测过程，提炼出 1 条候选经验，尚未通过验证，不会作为默认规则使用。

如果检索到有争议或已替代条目，回答中明确标注其状态并优先展示当前有效版本。知识条目被检索不等于它被采纳；展示应区分“提供参考”和“影响了本次决策”。

### 16.5 权限、隐私与可操作性

私有任务、项目经验和用户偏好只能对有权限的用户展示。公共专业知识与项目私有经验使用不同徽标和过滤边界。用户可以查看候选经验、提交纠正、标记不适用和请求归档；这些操作生成审计记录，不直接删除原始证据。

第一版必须支持：列表查看、条件筛选、详情查看、版本差异、来源定位、更新动态和聊天依据入口。批量编辑、复杂图谱可视化和自动生成可执行技能暂不作为首版依赖。

## 17. 以“更新卡片”作为统一展示组件

列表动态、详情历史和聊天依据可以共用更新卡片，降低实现复杂度。卡片结构为：

`变化类型 | 条目标题 | 当前状态 | 适用范围 | 更新原因 | 证据数量 | 更新时间 | 查看差异`

卡片点击进入版本对比，而不是展开完整长文本；详情页再展示原文、工具结果和关联任务。对用户影响较大的变化显示“可能影响当前项目”标记，该标记根据范围匹配和依赖关系计算，不由更新时间推断。

## 18. 展示层验收

使用预设样例验证：新增条目显示为候选或有效并带来源；修订条目能看见前后差异；被替代条目仍能查看历史；有争议条目不会被误显示为默认知识；同一次更新动态不重复；聊天回答能区分使用了哪些条目与仅供参考的条目；无权限用户看不到私有项目经验。

验收还要覆盖一条重要边界：向量检索命中但数据库条目已归档时，页面不得显示它为可用知识；检索索引内容与权威条目状态不一致时，以数据库状态和审计记录为准。

## 19. TencentDB-Agent-Memory 的借鉴价值

参考仓库：[TencentCloud/TencentDB-Agent-Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory)。本节基于仓库 README、安装说明、v3 接口文档和公开源码进行设计对照。它是通用 Agent 记忆平台，不是 MENET 领域知识库，也不应被视为对 MENET 预测效果的验证。

### 19.1 最值得借鉴的结构

**第一，分层记忆。**仓库把原始对话 L0、原子记忆 L1、场景记忆 L2 和长期核心/画像 L3 分开，并让生成与召回采用不同粒度。这正好可以映射到 MENET：

| TencentDB 层 | MENET 对应内容 | 是否保存原文 |
|---|---|---|
| L0 Conversation | 工具输入、用户明确指令、任务事件和原始输出引用 | 是，原始文件和日志留档 |
| L1 Atom | 数据版本、模型选择、兼容性事实、单条实验观察 | 关联证据，不用摘要代替原文 |
| L2 Scenario | 当前项目的研究目标、数据条件、阶段和已验证流程 | 保存结构化摘要与版本 |
| L3 Core / Persona | 用户长期偏好、团队约定、稳定工作方式 | 仅保存明确且长期有效的信息 |

MENET 需要对 L2 增加物种、性状、环境和数据集版本等领域边界；L3 不应保存未经验证的科研结论。分层的意义不是增加四个聊天窗口，而是让不同寿命、粒度和权限的内容分别治理。

**第二，资产化。**仓库不把记忆当作一张聊天记录表，而是把 Chat Memory、Skill、Wiki、CodeGraph 作为有状态资产管理，有 Owner、版本、可见性、绑定对象和使用记录。MENET 可以将知识条目、操作经验、项目状态和来源文档登记为资产，借此支持列表、审核、更新卡片和聊天依据展示。

**第三，异步沉淀。**仓库先写入 L0，再由后台 Pipeline 提炼 L1，之后在一定间隔生成 L2/L3；提炼失败不阻塞原始对话。MENET 可采用相同原则：任务完成或失败事件先落库，候选经验异步生成，工具输出核验后再激活。需要为任务完成事件设置幂等键，避免重试生成重复经验。

**第四，检索路由。**仓库采用关键词/BM25、向量检索和 RRF 融合，并限制条数、字符预算和超时。MENET 可先使用 SQLite FTS5，之后在有评测需求时增加向量召回；检索前按用户、项目、数据集版本、阶段和条目状态过滤，检索后再用数据库状态复核。不能把“召回命中”当作“允许使用”。

**第五，权限与装配。**仓库把 private、team、restricted 等可见性和 Agent 绑定分开处理。MENET 至少需要区分公共专业知识、用户私有偏好、项目私有经验和任务级临时信息。不同智能体角色可以有不同记忆装配：规划器偏重方法与约束，执行器偏重工具流程，解释器偏重结果与来源。

**第六，生成日志与使用统计。**仓库提供 memory prompt 和 generation log 的概念，并记录资产调用情况。MENET 可记录“哪些记忆被检索、哪些进入上下文、哪些影响了决策、结果是否成功”，用于发现无效记忆和评估策略；但调用次数不能单独证明知识正确。

### 19.2 对当前存储方案的具体影响

这个仓库反而支持“初期不必先上图数据库”的判断。其默认数据面是 SQLite，MongoDB 是可选的试验后端；关键词检索和可选向量能力也不要求用图数据库。仓库的 Wiki 和 CodeGraph 是结构化内容与关系索引能力，不等于整个记忆系统必须使用图数据库。

因此 MENET 第一版仍采用：SQLite 保存权威元数据、状态、版本、关系和审计；文件系统保存原始文档与分析产物；FTS5 做全文检索；后续按评测增量加入向量索引。仓库的 SQLite/MongoDB 可切换抽象值得借鉴，但不建议在 MENET 初期同时维护多个存储后端。

### 19.3 不宜直接照搬的部分

**不直接把 LLM 抽取结果当作正式知识。**通用聊天中的偏好和事实，与 MENET 的模型兼容性、指标解释和科研结论不同。候选经验仍须绑定任务、数据版本、工具输出和适用条件，并经过状态转换。

**不直接引入 Skill 执行机制。**仓库的 Skill 可以描述触发边界、步骤和验证规则，但 MENET 中涉及文件变换、训练和预测的操作必须由现有 Tool Layer 做参数校验、权限检查和幂等控制。第一版只保存操作经验和流程模板，不自动生成或激活可执行代码。

**不把 Wiki 代替领域知识图谱。**Wiki 适合文档结构、页面链接和快速阅读；MENET 的数据集、模型、任务和输出之间需要结构化关系和版本约束。两者可以共存：文档由 Wiki/全文检索承载，业务事实由 SQLite 业务表承载，关系表补充跨模块证据链接。

**不直接部署完整三件套。**仓库面向多 Agent 团队，包含 MemoryCore、MemoryHub 和 Proxy，运行依赖 Node 22、容器、LLM/embedding 配置及其服务边界。MENET 当前是已有 Web、后端、SQLite、任务和 MCP 架构，直接引入会增加网络服务、权限、数据迁移和运行维护成本。先吸收接口与治理思想，再决定是否把它作为独立记忆服务。

**不把通用 Benchmark 当成 MENET 评测。**仓库的 Agent 任务指标主要衡量记忆对通用任务的帮助；MENET 要额外评估数据集/模型匹配、预测前检查、重复错误率、引用支持率、跨版本恢复和研究结果解释。

### 19.4 推荐的借鉴顺序

1. 借鉴 L0-L3 的概念，在 MENET 中实现原始事件、原子事实、项目场景和长期偏好的边界。
2. 借鉴 Memory Asset 的状态、Owner、版本、可见性和绑定设计，完成知识列表、详情、更新动态和聊天依据。
3. 借鉴异步 Pipeline、幂等键和生成日志，实现任务结束后的候选经验提炼。
4. 先用 FTS5 做阶段化检索，再用独立评测决定是否加入 BM25/向量混合召回。
5. 在以上能力稳定后，再考虑单独部署 MemoryCore，或以内部服务接口吸收其能力；不把完整仓库作为 MENET 的领域知识层。

结论：TencentDB-Agent-Memory 可以作为 MENET 记忆子系统的架构参考，尤其适合借鉴“分层、资产化、异步沉淀、权限装配和可观测检索”。它不能替代 MENET 的数据版本、模型兼容性、实验证据和受控知识更新规则。对当前项目最稳妥的做法是先在现有 SQLite 和任务系统中实现这些原则，再根据实际规模决定是否引入外部记忆服务。

## 20. Semantica 的启示与规模判断

检查日期：2026-10-13。参考 [Semantica 仓库](https://github.com/semantica-agi/semantica)、ARCHITECTURE.md、pyproject.toml，以及 provenance、context 和 kg 模块的结构。检查的源码提交为 e247b94fbe4fc3a52bafae5997e48f1839e13b87，项目声明版本为 0.7.0。此次为文档与源码静态考察，未安装依赖或运行性能、正确性测试。

### 20.1 定位与适合借鉴的部分

Semantica 是以图为中心的知识与上下文工程框架，覆盖导入、解析、标准化、实体与关系抽取、冲突、去重、知识图谱、本体、推理、来源追踪、决策记录、存储、导出和展示。相较于 TencentDB-Agent-Memory 的记忆资产与团队使用流程，它更强调知识结构、上下文关联和决策可追溯性；两者能力存在重叠，这里只是面向 MENET 的侧重点比较。

对 MENET 首期优先借鉴四项原则：

1. **来源贯穿处理链。**从原始文档或工具输出，到片段、知识主张、经验、检索上下文，再到决策，均关联可定位来源。摘要不是新的独立证据。
2. **区分有效时间与记录时间。**Semantica 的 kg 模块提供 BiTemporalFact 等时间建模结构。MENET 可增加 valid_from、valid_to、recorded_at 与 superseded_at，区分何时适用和何时获知；未知有效时间留空并说明，不以导入日期替代。
3. **记录决策及其输入。**参考 context 中的 DecisionRecorder，记录用户目标、候选模型、排除原因、适用知识版本、实际检查结果、最终选择与执行结果。记录的是外部可观察依据，不是大模型隐藏推理。
4. **统一实体身份和条件。**数据集版本、性状、模型、环境、预处理配置采用受控字段与唯一身份。同名性状和相似文本不能直接合并；冲突先检查条件差异，再判断是否真矛盾。

这些原则可以落到现有 sources、memory_evidence、memory_relations、memory_changes 和 task_events 中，无需先迁移到图数据库。补充 decision_records 表：decision_id、task_id、goal_snapshot、candidate_references、check_event_ids、memory_revision_ids、selected_object_reference、policy_version、outcome_reference、recorded_at。大型检查结果用引用保存。

### 20.2 是否过重

整体采用对 MENET 第一版偏重，主要负担是需要选择和维护多套知识表示、抽取方法、规则与存储接口，而不是仅看仓库文件大小。其基础依赖声明包含 NumPy、SciPy、scikit-learn、Pandas、RDFLib、NetworkX、PyArrow、Pydantic 等；图数据库、向量数据库、本地模型和文档解析等另有可选依赖。

因此它并非必须启动所有服务或图数据库，但最小安装也不是只有几个轻量依赖。当前依赖声明包含 numpy>=2.0.2 和 pydantic>=2.13.4 等约束，可能影响已有训练环境；实际冲突须依据 MENET 的依赖清单验证，不能在未检查时断言不兼容。

首期借鉴 schema 与流程，不安装完整框架或 all extras。未来确需模块时，在独立环境选取模块、固定版本，用脱敏文档和业务场景验证结果质量、来源保留、时延、内存与部署成本，再决定通过适配接口接入。

### 20.3 使用边界与后续触发条件

确定性规则推理只保证按给定规则执行，不保证输入事实或规则科学正确；记录原因链也不构成因果效应证据。实体自动合并、关系预测和自动冲突消解均产生候选，不直接改变模型兼容性或正式科研结论。

出现以下实际需求时再考虑引入模块：大量文献需要统一实体与关系；数据、模型、结果和经验需经常进行多跳影响查询；需要 RDF/OWL/SHACL 等外部语义标准交换与验证。先用小范围对比证明收益，不因框架提供某功能就扩大项目范围。

### 20.4 对现有方案的调整

保持 SQLite、文件、全文检索及可选向量索引的首期架构；补充知识有效时间与记录时间，增加决策记录及模型排除原因，在知识详情中展示来源链，在预测结果中提供“为何选择此模型”的可展开依据。图展示先展示有限的证据和依赖关系，不必渲染整个知识网络。

首期验收增加：可还原某次决策当时读取的知识版本；晚导入的旧文档不会被误判为最新知识；同名不同数据版本的实体不误合并；关系中的原因说明不会被展示为经验证的因果结论。

## 21. 当前实施范围确认：知识辅助理解与上下文记忆

确认日期：2026-10-14。状态：用户确认的知识层设计范围，尚未实施。参数优化另按第 22 节作为必须实现的能力；本节不再排除受控调参，但完整记忆进化与复杂展示不作为首版要求。

### 21.1 目标与当前基础

知识层让系统在处理用户问题时，把相关的 MENET 专业知识、有效项目状态与必要的历史实验信息一并提供给 LLM，使回答和操作建议更符合项目实际、减少猜测并能说明依据。知识层本身不保证预测精度提高；当用户请求优化时，必须由第 22 节的受控参数实验验证建议，不允许无授权自行开展实验或自动改写算法。

当前系统不是完全没有知识与记忆：LLM 有其已有知识，程序有提示词和固定规则，业务系统也已保存会话、数据集、任务和模型记录。缺少的是可检索、可引用的 MENET 专用知识，以及对历史上下文的有效装配。

当前核查结果：

- `messages` 保存聊天历史，但 `AgentIntentParser.parse()` 的 LLM 请求主要使用当前一句用户输入，没有将相关历史装配为上下文。
- `conversations.state_json` 保存当前数据集、性状、模型、任务等状态，可以作为短期上下文基础，不必重新建立一套重复状态源。
- `tasks`、`trained_models` 和结果文件保存实际实验事实，可供受权限约束的历史查询；精确指标、模型状态和文件兼容性仍需实时核验。
- 当前聊天意图限定在检查、训练、预测、评估、解释和模型查询等操作；专业知识问答需要增加明确的只读路由，不能仅建知识库却仍将问答判为不支持操作。

### 21.2 知识与记忆层的三类能力（参数优化见第 22 节）

| 能力 | 首版内容 | 不承担的职责 |
| --- | --- | --- |
| 专业知识检索 | MENET 原理、CSV/PLINK/`.pheno` 格式要求、参数说明、预处理与指标解释；回答关联文档位置和版本 | 不将论文某次结果直接变为默认运行参数 |
| 上下文记忆 | 当前数据集、性状、模型、待完成任务、用户明确选择，以及少量相关历史 | 不擅自将一次指示变为长期偏好，不跨用户共享私有内容 |
| 历史实验查询 | 查询真实任务、配置、状态与结果，为“之前做过什么”“本次有什么不同”提供依据 | 不自动提炼和激活通用科研经验，不自行提交新实验 |

优先复用现有业务记录；跨会话的长期偏好和独立研究项目状态有明确需求后再增加。模型、数据或预处理版本改变时，重新核验依赖关系；多个“上次任务”均合理时询问用户，不猜测。

### 21.3 接入现有 harness 的流程

```text
用户输入
  -> harness 获取可信身份、页面选择和有效会话状态
  -> 获取少量相关历史，识别操作请求或只读知识问答
  -> 按权限、对象版本、任务阶段检索相关知识与实验记录
  -> 将用户问题、上下文和带来源的知识分别提供给 LLM
  -> LLM 给出回答或结构化操作建议
  -> 程序校验并执行用户请求范围内的已有工具
  -> 根据真实结果生成解释，页面展示来源依据
```

LLM 提取的数据集或模型引用由后端解析并核验，不能从文档片段猜出可执行路径。工具执行后的解释使用实际结果与相关知识，不用记忆摘要代替真实指标。知识问答只读，不因为检索到某种操作方法就自动训练、修改数据或执行命令。

接口建议：扩展意图解析的上下文输入；增加只读知识问答路径；在结果解释前调用统一的上下文检索服务。知识检索和实验查询可通过内部服务复用，首版不要求更换现有 harness，也不以 Codex 集成为前置条件。

### 21.4 知识、记忆与规则的边界

- 专业知识用于解释方法与提供参考；会话记忆用于恢复用户目标；历史记录用于核验发生过的事实。
- 权限、参数范围、模型兼容性、资源限制与模型选择政策仍由程序强制执行，检索文本不能覆盖这些规则。
- 已发现的 `0.05` 模型切换阈值与 LLM 推荐路径不一致，需要独立统一后端政策；不能通过“记住用户认可了阈值”来代替代码修复。
- 专业知识有来源不等于必然正确；缺少来源、条件不满足或来源冲突时说明不确定性。返回“未知”优于编造项目事实。
- 当前请求中的明确选择优先于历史默认；历史中模型已归档、数据已删除等情况，以当前业务记录为准。
- 文档和历史消息作为数据提供，不作为更高优先级指令。只发送必要摘要与字段，不把 GB 级基因型、敏感信息或其他用户数据送给 LLM。

### 21.5 轻量实现与顺序

1. 整理当前有效的 MENET 说明与项目操作文档，标注来源、版本、章节和适用范围，排除已被新实现取代的旧操作说明。
2. 实现有界的文档片段检索，先采用精确匹配和关键词/全文检索；验证中文与中英文混合查询。存储选择需遵守 login 统一写入及共享存储可靠性边界，不默认延续跨节点 SQLite 访问。
3. 将可信会话状态、少量相关历史和经核验的实验摘要装配给 LLM，明确区分用户原话、程序事实和文档证据。
4. 增加只读知识问答与回答引用；首版提供简洁的“本次依据”展开区即可，完整知识管理页面、版本差异和更新动态不作为第一版前置要求。
5. 通过固定业务问题检验准确性、来源支持、上下文恢复、权限和延迟；只有发现明显召回不足时再评估向量索引。

知识服务不可用时，标准任务回退到原有流程；专业问答明确提示知识检索不可用，不伪装成有文档依据。所有新增内容需做增量迁移，保留已有 CSV、多性状与 PLINK 流程。

### 21.6 当前不实施的内容

- MENET 算法自我迭代、自动修改代码、网络结构或生产规则。
- 未经用户授权的主动实验、超出批准预算的 GPU 使用，以及自动修改算法代码；受控参数优化不在排除范围内，按第 22 节实施。
- 自动提炼并激活跨数据集经验、自动生成可执行技能。
- 记忆策略自进化、复杂知识图谱、完整外部记忆平台部署。

前文对应内容保留为可选研究方向，不因文档中已有设计而自动纳入开发。

### 21.7 首版验收与预期收益

- 能根据当前软件说明解释 PLINK 文件、性状选择、预处理和指标，引用确实支持回答。
- 能在上下文明确时理解“使用刚才的模型”“继续上次的预测”；有歧义时澄清，真正执行仍依据用户授权。
- 能从实际业务记录回答历史训练情况，不把旧模型、旧数据或记忆中的过时指标当作现状。
- 无权限用户无法检索他人的会话、实验和私有知识；文档内容不能诱导越权调用工具。
- 以相同 LLM 和工具，对比接入前后的回答准确性、引用支持、上下文恢复和延迟，不以知识条目数量或模型自评作为成功标准。

预期收益是更准确、有依据、连续的理解与解释，而非保证每次回答都改善或预测 R² 自动提升。知识与记忆层补充上下文，不改变 MENET 训练与预测的数学实现。

## 22. 必须实现：知识指导的受控参数优化

确认日期：2026-10-14。状态：必须实现的产品能力，尚未完成，不代表已支持自动调参。这一确认修正此前“暂不做自动调参”的范围：可以分阶段交付，但不能只返回建议就宣称已经完成优化。

### 22.1 参数优化不等于算法自我迭代

- 参数优化保持 MENET 算法和网络结构不变，在有明确类型、范围和实际配置映射的参数中寻找更适合当前数据的配置。
- 学习率、batch size、dropout、训练轮数等优先纳入；weight decay、margin 等须先核查当前训练实现是否支持，未接入的参数不能展示为可生效选项。
- 不自动修改源码、损失函数、网络结构或生产规则，不保证优化必然提升预测表现。
- 用户仅问“怎样优化”时给出解释和方案；用户明确请求执行且预算/授权已确定后，才提交实验。信息不足先询问，禁止无限试验。

### 22.2 知识如何让建议更精准：DTT 示例

用户问：“DTT 效果不理想，把训练轮数从 30 增加到 100，会不会更好？”

未接入项目知识时，LLM 容易只给出“增加轮数可能改善训练，注意过拟合”的一般性建议。接入后，harness 应提供：参数说明及其作用阶段、当前有效配置、真实 train/validation 曲线、可比较历史实验，以及不得用最终测试集反复调参的验证规范。

以下是说明机制的假设示例，不是对当前 DTT 曲线的实际诊断：

- 若训练表现继续改善而验证表现停滞或下降，LLM 应说明“不支持直接增加到 100 轮”，先检查最佳验证轮次，提出有限的学习率或正则化候选。曲线只能支持假设，不能单独证明根因。
- 若训练和验证表现都仍有改善趋势，可以提出适度增加轮数的候选实验，而不是凭经验默认加强正则化。
- 若缺少逐轮曲线或可靠历史记录，应明确证据不足，不虚构过拟合、最佳轮次或预期收益。

知识提供判断方法，实际实验记录提供当前证据，真实训练验证候选建议；三者不能相互替代。参数说明须区分编码器与 MENET 主模型，避免用户以为只改一处，实际却同时改变两个阶段。

### 22.3 请求“在限定预算内优化”的执行闭环

```text
读取授权范围内的数据版本、预处理、配置、划分和训练曲线
  -> 检索相关方法知识与可比较历史实验
  -> LLM 提出少量候选及依据，后端校验参数和预算
  -> 用户确认计划，或使用当前请求中已明确批准的预算
  -> 固定比较协议，按实验组提交候选训练
  -> 用验证集/交叉验证比较表现、波动和资源消耗
  -> 预算内决定继续或停止，冻结最终配置
  -> 最终独立测试，返回推荐模型、配置和完整实验记录
```

默认不自动替换用户当前模型：展示候选与基线比较，由用户确认采用；仅在用户预先明确授权自动采用时按登记政策执行。没有可靠改善时保留原模型，并如实报告已完成实验与局限。

### 22.4 工程要求与最小交付

1. **证据读取**：读取完整配置和训练/验证曲线，关联 task_id、model_id、数据及预处理版本；区分用户请求值和实际有效值。
2. **受控覆盖**：建立任务级参数 schema、范围和配置映射，训练保存有效配置快照；不能依赖 LLM 修改全局配置文件，也不能影响普通训练和 CSV 上传方式。
3. **实验组**：记录 group_id、基线任务、候选配置、固定划分、种子、方法版本、状态、指标与输出引用，支持幂等提交、取消和重启后恢复。
4. **预算执行**：服务端限制候选数、最大轮数、并发、单作业 walltime 和累计计算预算。重试计入预算；接近上限时不提交新作业，超限运行按明确策略停止。排队时间与执行时间分别统计。
5. **可比评估**：基线和候选使用相同数据、预处理与验证协议；需要稳定性判断时使用多种子或交叉验证。筛选依据不能是最终测试 R²，也不能用现有 `0.05` 测试指标切换规则选择超参数。
6. **结果解释**：区分“候选建议”“单次观察”“重复验证支持”，给出引用、成本与局限，不宣称未知收益。

优先交付少量参数、有限候选、顺序运行的原型；无需先接入复杂图谱、自动经验进化或算法改写。知识增强与调参工具可以并行规划，但只有工具、预算、实验比较均接通后才开放“执行优化”入口。

### 22.5 必须通过的验收

- 修改参数实际影响相应训练阶段，并可由配置快照核验；非法或未支持的参数被拒绝。
- “DTT 效果不理想，请在限定预算内优化”能进入明确的优化流程，预算不明时询问，不误解析为一次默认训练或只给建议后显示“优化完成”。
- 未授权、越权及重复提交不会产生额外 GPU 作业；达到预算或用户取消后不再提交候选。
- 保存并展示基线与候选验证结果、种子、配置、失败与资源记录，不混用不兼容的数据版本。
- 缺少曲线时不编造诊断；没有改善时明确报告，不强制采用新模型。
- 保留最终测试的独立性，完整记录此前是否已使用该测试集参与选择；已暴露的历史测试成绩不能重新宣称为未使用的独立证据。

本次文档修订不实际提交实验、不安装依赖、不修改服务运行逻辑；后续实施需按以上能力清单逐项验证。

### 22.6 为什么暂不自动改写算法：验证难度与投入产出

决策日期：2026-10-14。暂不实现算法自动改写，是当前阶段的投入产出和风险控制选择，不是认定技术上不能实现。受控参数优化仍为必须能力。

**关键判断：生成一个能运行的代码版本，不等于证明它是一个更好的算法。** 自动修改 MENET 源码、网络结构、损失函数或特征融合方式后，必须有独立于提案者的程序评测，并由人审核实验设计、结果解释与是否发布；不能让生成改动的 LLM 自评后直接替换生产版本。程序负责一致、可重复的测量，人负责审查测量是否回答了正确的问题，两者可以结合，不要求人逐个手工训练。

主要难点与成本：

| 难点 | 必须验证什么 | 为什么成本较高 |
| --- | --- | --- |
| 实现正确性 | 张量形状、梯度、损失、数值稳定性与模型保存/加载 | 能启动或单次训练成功不能排除隐蔽错误，需要单元测试、冒烟测试和回归检查 |
| 公平比较 | 相同数据/预处理/划分，记录原版与候选配置及计算预算 | 不能让新结构获得更多调参机会或训练资源后，直接将收益归因于算法 |
| 稳定性 | 多随机种子、适当的重复划分或交叉验证，报告波动 | 一个候选通常需要多次训练；搜索多个候选会进一步放大 GPU 时间和排队成本 |
| 泛化与研究有效性 | 明确提升针对哪个性状、数据集、群体或环境，必要时独立数据验证 | 在单个 DTT 实验上更好，不等于可替换其他场景的 MENET 实现 |
| 评估泄漏与选择偏差 | 开发时只用训练/验证，候选冻结后独立测试 | 反复按测试成绩修改算法会消耗测试独立性；需要保留并维护可信评估数据 |
| 改动归因 | 消融或控制实验，区分结构收益与参数、随机性及实现修复 | 多项改动一起提交时，即使分数提高，也难确定哪项真正有效 |
| 产品兼容性 | 原模型资产、推理接口、文件格式、资源上限和现有用户流程 | 新模型可能不兼容旧 checkpoint，必须做版本管理、发布审核与回退 |

参数优化同样需要真实实验和公平验证，并非没有计算成本；但参数空间可限制、算法与接口保持固定，测试与兼容性负担相对可控。算法改写增加了开放式结构搜索、代码正确性和发布维护成本。当前不具备足够证据量化所需时长或预期提升，因此不写未经测量的收益与耗时承诺。

当前优先把资源投入真实数据支持、可靠任务执行、知识辅助建议和有预算的参数优化。只有当这些能力稳定，且固定算法下的参数优化仍不足以满足明确目标时，再评估算法改写。不能为了展示“自我进化”而自动开展大量实验。

若未来启用，最小流程应为：明确假设 -> 独立实验分支生成候选 -> 正确性与兼容性检查 -> 固定协议评测 -> 必要的重复验证/消融 -> 人工审核 -> 版本化发布与可回退部署。提案者不能自行修改评估标准；任何不满足门槛的候选保留为实验结果，不进入生产。
